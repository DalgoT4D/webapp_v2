# Analytics & Feature Tracking (PostHog)

**Instrument every new feature** — breadth (a feature is visited) and depth (key actions). Skipping analytics on a new feature is a review-blocker.

- **Event names live in `constants/analytics.ts`** — fixed strings in `category:object_action` snake_case. Never interpolate variables into a name; pass them as properties. Add new events to `ANALYTICS_EVENTS`.
- **Fire via `trackEvent(ANALYTICS_EVENTS.X, { props })`** from `lib/analytics.ts`, in the **success path** (after the API call resolves), **fire-and-forget** — never `await` it, never let it throw into the handler.
- **"After the await" is not the same as "on success"** — many helpers here handle their own errors (a toast, an inline status) and resolve normally either way: `saveDashboard`, the builder's `cleanup`, `usePdfDownload().download`, `copyUrlToClipboard`. Awaiting one of those and then firing counts *failures* as successes. Such a helper must return a success boolean and the caller must gate on it (`const ok = await x(); if (ok) trackEvent(...)`). Check this whenever an event sits next to an `await` that isn't inside a `try` whose `catch` skips the event.
- **New page/route/tab** → add to the `FEATURES` map + `PATHNAME_TO_FEATURE` in `constants/analytics.ts`; `feature:viewed` then fires automatically on navigation. Tabs (local/query state) need an explicit `trackFeatureView(FEATURES.X, { tab })` in the tab `onChange`.
- **Don't add user/org/role to event properties** — the person (`user_id`, `is_internal`) comes from `identify`, and `role` / `org_slug` / `org_name` / `org_plan` are **super properties** registered in `lib/analytics.ts`, so they already ride every event. Only add properties that segment _within_ an event (e.g. `chart_type`, `format`, `is_public`).
- **The `organization` GROUP is the canonical org dimension — build org metrics on it.** `posthog.group('organization', …)` puts `$group_0` on every event, and the existing metric family already depends on it: `math: unique_group` + `math_group_type_index: 0` (Weekly/Daily active orgs), `{"key": "subscription_plan", "type": "group", "group_type_index": 0}` (Org Value Retention), and `LEFT JOIN groups g ON g.key = e.$group_0` reading `g.properties.subscription_plan` / `g.properties.name` (Feature Breadth by Plan, Org-Health States, the client heatmaps). A new org metric that uses anything else silently stops being comparable with those, so use the group. The `org_*` super properties are a **convenience layer** for quick one-off filters, not a second source of truth. (The Groups *settings* page advertises a paid addon; group properties, `$group_0`, and the `groups` table all work regardless — verified against live data.)
- **Onboarding walkthroughs report through the unified `onboarding:path_*` events** — `path_started` / `path_stage_viewed` / `path_resumed` / `path_completed` / `path_exited`, each carrying `path` (see `ONBOARDING_PATHS`), all fired from `lib/onboarding-analytics.ts`. A new walkthrough adds a `path` value, not a new event family. Each flow's own legacy events (`tour_*`, `insight_walkthrough_*`) keep firing — existing insights depend on them. The path lifecycle starts at the point a path is actually chosen (the insight fork, not `start()`), or nothing would attribute correctly. Silent abandonment fires nothing by design: derive it as `started - completed - exited`.
- **Path duration is measured in the client, session duration is not** — an onboarding path survives reloads and spans days, so PostHog's own `$session_duration` (free, automatic, no code) measures a different thing. `duration_seconds` on `path_completed`/`path_exited` comes from a `localStorage` start stamp, and is **omitted rather than sent as 0** when no stamp exists — a fake 0 would drag every average down. Cross-check a suspicious duration against a funnel's built-in time-to-convert, which uses ingest timestamps and needs no client state.
- **Full CRUD per feature** — every feature fires `*_created`, `*_updated`, and `*_deleted` on the success path. In shared create/edit forms, guard so `*_created` fires only on the create branch and `*_updated` only on the update branch. Fire `*_deleted` after the delete API resolves (in the confirm handler).
- **Dashboards fire `dashboard_updated` on editor-open as well as save** — a product decision, not an oversight: the two save buttons and EDIT DASHBOARD all fire it, each with its own `source` (`DASHBOARD_UPDATE_SOURCES`). The open path persists nothing, so the raw event total mixes opens with saves — always send `source` so `source != 'edit_button'` can recover a true save count. Track editor-open once where the editor mounts (`app/dashboards/[id]/edit/page.tsx`) rather than per button — one place covers every entry link — ref-guarded, and skip the post-create redirect (`?new=true`) so a creation isn't also counted as an update.
- **Automatic work is never tracked** — an event must correspond to something the user did. The alert wizard's Test step dry-runs from a `useEffect` on every payload change, so it measures the wizard, not the user; a wizard-step event (`alert:wizard_step_viewed`, `kpi:wizard_step_viewed`) is what measures reaching that step and where people abandon. Same reasoning as autosave below.
- **Autosave is never tracked** — where a builder autosaves on a debounce (dashboards, every 5s), `*_updated` fires only on an explicit user save. Autosave is time-triggered rather than intent, would emit dozens of events per session into a value-action metric, and (because `useDebounce` seeds with its initial value) fires once on mount too — so tracking it logs builder *opens* as edits.
- **Sharing is two events, not one toggle** — `*_made_public` when public access is switched ON (switching it OFF fires nothing; one event for both directions makes the total meaningless), and `*_shared` for the actual share act. Track both at every entry point — dashboards have two (the dashboard view and the list row menu), reports two (the link dialog and the email dialog, split by `source`), all feeding the same `components/ui/share-modal`, which stays analytics-free. Emailing sends `recipients_count` only; **recipient addresses are PII**.
- **Public/anonymous view events** — `public_*_viewed` carries `org_name` (and `org_slug` where the payload has it) since there is no person or org group to attach, is **never** a value action (anonymous devices would pollute a unique-users count), and must exclude machine renders: a `?print=true` PDF-capture pass renders the same public component, so guard on it or every export logs a view.
- **Name the event after what actually changes** — a report snapshot is frozen, so its editable field gets `report:summary_updated`, not `report_updated`. Don't imply mutability the feature doesn't have.
- **Comment threads** — comments are flat per target (no `parent_id`), so a reply is a comment on a target that already has a live one, carried as `is_reply` + `thread_size` on one `comment_created` event. Read the thread size **before** posting — the `mutate()` afterwards makes every comment look like a reply. Never send comment content, author emails, or mentioned emails; a `mention_count` is fine, and "who commented" already comes from the attached person.
- **One event per lifecycle action, paths go in `source`** — when several UI paths produce the same outcome, fire ONE event and distinguish them with a `source` property from a named constant (see `CHART_CREATE_SOURCES`). Charts do this: new build, save-as-new, and duplicate all fire `chart:chart_created` with a different `source`. Don't mint `*_saved_as_new` / `*_duplicated` events — they make the headline total a hand-summed formula and silently miss any path added later.
- **Include the resource id** — every resource event carries its own id (`chart_id`, `dashboard_id`, …) so `created → viewed → deleted` can be joined for one resource ("created but never opened"). Filter/join by it; never _break down_ by it (unbounded cardinality). Read the id before a delete/mutate — after `mutate()` the row is gone from local state. Sub-events count too: a tab, filter, or element event without its `dashboard_id` can't answer "which dashboards use tabs". Where the firing component doesn't have the id (`TabBar`, `text-element-unified`), either move the event up to the parent handler that does, or thread the id down as an analytics-only prop — never substitute a share token or other secret for it.
- **Long-running actions: fire on start, not outcome** — for async work (sync, pipeline run, dbt run) fire `*_triggered` once the request is accepted. Do **not** add success/failure/duration/rows-synced events to PostHog. By design those live elsewhere: **errors/failures → Sentry; operational outcomes & volume → internal dashboards** (sourced from the warehouse/backend). PostHog is scoped to product/feature-adoption only.
- **Never send PII or customer data** — identify by backend `user_id`, never email (email is used only locally to compute `is_internal`). Also **never send warehouse-data-derived strings**: no `schema_name`, `table_name`, column names, source/connection _instance_ names, file names, or recipient emails. Safe properties are categorical types/enums (`chart_type`, `warehouse_type`, `source_type` = connector type, `aggregation`, `filter_type`), counts, booleans, and opaque internal IDs.
- **No purposeful action-button missed** — every button/control that calls an API, mutates state, or triggers work gets an event (view + full CRUD + primary-use run/sync/deploy/publish + share/export/download + invite/role/account actions). The test: "does clicking this _do_ something?" → log it. Only skip pure UI mechanics with no analytic value: sort, filter, paginate, panel resize/minimize/fullscreen, a plain reload/refresh, back/nav buttons (destination is already covered by `feature:viewed`), and opening a form (the form's save is what fires).
